\subsection{Relational queries in SQL}
\label{sec:sql}

SQL is the standard language for working with relational databases.
It is declarative in that a statement describes the desired result,
and the database system determines how to compute it.
Its statements can be assigned to one of three groups:
the Data Query Language (DQL) reads data,
the Data Manipulation Language (DML) adds, rewrites and removes rows,
and the Data Definition Language (DDL) defines the tables themselves.

\subsubsection{Query shape}

The core of a DQL statement, concisely referred to as a query,
consists of three clauses:

\begin{sqlblock}
SELECT name, email AS email_address
FROM users
WHERE name = 'Bob';
\end{sqlblock}

\mono{FROM} chooses the source rows,
\mono{WHERE} keeps only the rows matching its condition,
and \mono{SELECT} chooses the output columns.
Conditions compare values from columns or literals
(\mono{=}, \mono{<>}, \mono{<}, \mono{>}, \mono{<=}, \mono{>=})
and combine with \mono{AND}, \mono{OR} and \mono{NOT}.
Although \mono{SELECT} is written first, it is evaluated after \mono{WHERE}.
Filtering happens before projection (the choosing of output columns),
so a \mono{WHERE} clause cannot refer to an alias defined in \mono{SELECT}.
\mono{SELECT} may also compute output columns from expressions
and rename them with \mono{AS}. \mono{SELECT *} keeps all columns.

\subsubsection{Sorting and limiting results}

\mono{ORDER BY} sorts the result rows by one or more expressions,
each ascending (\mono{ASC}, the default) or descending (\mono{DESC}).
Multiple keys apply left to right:

\begin{sqlblock}
SELECT id, total
FROM orders
ORDER BY total DESC, id ASC
LIMIT 2;
\end{sqlblock}

\mono{LIMIT n} keeps only the first \mono{n} rows,
and \mono{OFFSET n} skips the first \mono{n} rows,
together they implement pagination.
Rows that compare equal on all sort keys keep an unspecified relative order,
so reproducible paging needs a unique key, typically the primary key, as the last sort key.

\subsubsection{Joining tables}

\mono{JOIN} pairs rows from two tables according to a condition in \mono{ON},
usually a foreign key compared with the primary key it refers to:

\begin{sqlblock}
SELECT orders.id, orders.total, users.name
FROM orders
JOIN users ON orders.user_id = users.id;
\end{sqlblock}

A plain \mono{JOIN} is an inner join, which drops pairs that match nothing.
In the above statement, the result holds one row per order,
each extended with its user's name.
Multiple joins can be chained, which is how join tables are read.
\mono{users} joined with \mono{user\_roles} and then with \mono{roles}
yields one flat row per membership:

\begin{table}[H]
	\centering
	\begin{tabular}{|l|l|}
		\hline
		\texttt{user} & \texttt{role} \\
		\hline
		Alice         & admin         \\
		Alice         & editor        \\
		Bob           & editor        \\
		\hline
	\end{tabular}
	\caption{Rows from joining \mono{users} through \mono{user\_roles} to \mono{roles}.}
	\label{tab:memberships}
\end{table}

Unlike the inner join, outer joins keep rows
that match nothing on the other side.
A \mono{LEFT JOIN} keeps every row of the left table,
a \mono{RIGHT JOIN} every row of the right table,
and a \mono{FULL JOIN} keeps all rows from both sides,
filling missing columns with \mono{NULL}.
Tables can also be joined with themselves
when a foreign key points into its own table,
for example a \mono{manager\_id} column referring to \mono{users.id}.
Each occurrence then needs a distinct alias
with \mono{AS} to tell the two roles apart:

\begin{sqlblock}
SELECT employee.name, manager.name AS manager
FROM users AS employee
JOIN users AS manager ON employee.manager_id = manager.id;
\end{sqlblock}

\subsubsection{Missing values}

\mono{NULL} marks a value as absent or unknown.
It is itself not a value but the absence of one.
Unlike \mono{0}, the empty string and false,
which are ordinary values of their respective types,
\mono{NULL} is distinct from every value of every type.
Unknown values have special propagation behavior.
Any comparison or arithmetic involving \mono{NULL}
yields \mono{UNKNOWN} or \mono{NULL} rather than a concrete value,
for example \mono{NULL = 1} is \mono{UNKNOWN} and \mono{1 + NULL} is \mono{NULL}.
\mono{UNKNOWN} is a third truth value besides \mono{TRUE} and \mono{FALSE},
which are known collectively as three-valued logic (3VL).
This system requires careful handling of propagation rules
and attention to the behavior of the value's consumer,
for example \mono{WHERE} keeps only rows whose condition is \mono{TRUE},
whereas \mono{CHECK} constraints reject only \mono{FALSE},
so \mono{UNKNOWN} does not always behave like either other truth value.
The ordinary comparison operators cannot detect absence,
which is why \mono{NULL} has dedicated ones: \mono{IS NULL} and \mono{IS NOT NULL}.

\begin{sqlblock}
SELECT name FROM users WHERE email IS NULL;
SELECT name FROM users WHERE email IS NOT NULL;
\end{sqlblock}

The same idea applies to aggregation, which combines the known inputs
and cannot process unknown ones, so they skip \mono{NULL}.
Where there is nothing to combine,
the result itself may have undefined semantics,
for example \mono{SUM} and \mono{AVG} over an empty set of rows
return \mono{NULL}, not zero.

\subsubsection{Aggregation}

Functions like \mono{COUNT}, \mono{SUM}, \mono{AVG}, \mono{MIN} and \mono{MAX}
collapse a set of rows into a single value.
Without further clauses the whole result becomes one row.
\mono{GROUP BY} separates rows sharing the same values to be aggregated separately,
yielding one result row per group:

\begin{sqlblock}
SELECT user_id, COUNT(*) AS order_count, SUM(total) AS total_spent
FROM orders
GROUP BY user_id;
\end{sqlblock}

This returns one row per user:

\begin{table}[H]
	\centering
	\begin{tabular}{|c|c|c|}
		\hline
		\texttt{user\_id} & \texttt{order\_count} & \texttt{total\_spent} \\
		\hline
		1                 & 2                     & 141.50                \\
		2                 & 1                     & 7.00                  \\
		\hline
	\end{tabular}
	\caption{Orders aggregated per user.}
	\label{tab:order-totals}
\end{table}

\mono{HAVING} filters groups after aggregation,
mirroring how \mono{WHERE} filters rows before it,
for example \mono{HAVING COUNT(*) > 1} keeps only users with more than one order.

\subsubsection{Subqueries}

A query can appear inside another query wherever a value, a list or a table is expected.
Scalar subqueries in \mono{SELECT} must return a single row with a single column,
and compute one value per result row:

\begin{sqlblock}
SELECT name,
       (SELECT COUNT(*) FROM orders WHERE orders.user_id = users.id) AS order_count
FROM users;
\end{sqlblock}

This returns the name and number of orders for each user.
Because the inner query refers to an outer row (\mono{users.id}),
it is correlated, which means it is evaluated once per outer row.
An uncorrelated subquery is independent of the outer query and runs only once,
for example a subquery on the right of \mono{IN},
which must return any number of rows with a single column:

\begin{sqlblock}
SELECT name FROM users
WHERE id IN (SELECT user_id FROM user_roles WHERE role_id = 1);
\end{sqlblock}

A subquery in \mono{FROM} can take any shape and acts as a derived table:

\begin{sqlblock}
SELECT * FROM (SELECT * FROM users WHERE name <> 'Bob') AS filtered;
\end{sqlblock}

\subsubsection{Row-level computation}

\mono{CASE} chooses a value per row from a chain of conditions:

\begin{sqlblock}
SELECT id, total,
       CASE WHEN total >= 100 THEN 'large'
            WHEN total >= 10 THEN 'medium'
            ELSE 'small' END AS size
FROM orders;
\end{sqlblock}

Scalar functions compute new values from existing ones, for example
\mono{LENGTH(s)} counts characters, \mono{UPPER(s)} and \mono{LOWER(s)} change case,
and \mono{CAST(x AS TEXT)} converts between types.
\mono{COALESCE(a, b, ...)} is an example of a variadic scalar function and
returns its first non-\mono{NULL} argument, commonly used to express defaults:

\begin{sqlblock}
SELECT users.name, COALESCE(profiles.bio, 'no bio') AS bio
FROM users
LEFT JOIN profiles ON profiles.user_id = users.id;
\end{sqlblock}

\subsubsection{Window functions}

Window functions compute over a group of related rows,
called a partition, without collapsing them, unlike plain aggregation.
An \mono{OVER} clause defines the window,
consisting of \mono{PARTITION BY}, which divides rows into groups,
and \mono{ORDER BY} to order rows within each group.
An empty \mono{OVER ()} takes the result over all rows as a single group.
For example, \mono{ROW\_NUMBER()} numbers the rows of each partition in order:

\begin{sqlblock}
SELECT id, user_id, total,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn
FROM orders;
\end{sqlblock}

Alice's orders are numbered 1 (99.50) and 2 (42.00),
Bob's single order is number 1.
The output order itself is unspecified without an outer \mono{ORDER BY}.

\begin{table}[H]
	\centering
	\begin{tabular}{|c|c|c|c|}
		\hline
		\texttt{id} & \texttt{user\_id} & \texttt{total} & \texttt{rn} \\
		\hline
		1           & 1                 & 42.00          & 2           \\
		2           & 1                 & 99.50          & 1           \\
		3           & 2                 & 7.00           & 1           \\
		\hline
	\end{tabular}
	\caption{Orders numbered per user by descending total.}
	\label{tab:row-number}
\end{table}

Other window functions include \mono{RANK()}, which numbers with gaps for ties,
and aggregates like \mono{SUM(total) OVER (PARTITION BY user\_id)},
attaching each group's total to every row.

\subsubsection{Changing data}

Adding, rewriting and removing rows belongs to the Data Manipulation Language (DML).
\mono{INSERT} adds rows, \mono{UPDATE} rewrites columns of the rows
matching its \mono{WHERE} clause, and \mono{DELETE} removes them:

\begin{sqlblock}
INSERT INTO users (name, email) VALUES ('Carol', 'carol@example.com');
UPDATE users SET email = 'bob-new@example.com' WHERE name = 'Bob';
DELETE FROM users WHERE name = 'Carol';
\end{sqlblock}

Omitting \mono{WHERE} in \mono{UPDATE} or \mono{DELETE} affects every row.
DML statements between \mono{BEGIN} and \mono{COMMIT} form a transaction.
Either all of them take effect or,
if any fails and the transaction is rolled back with \mono{ROLLBACK}, none does.
This makes the entire transaction atomic.

\subsubsection{Defining structure}

The Data Definition Language (DDL) is used to define the tables
that DQL reads and DML changes.
\mono{CREATE TABLE} names a table and declares its columns along with their types,
as well as constraints, such as foreign keys or nullability.
\mono{ALTER TABLE} changes an existing table, for example by adding a column,
and \mono{DROP TABLE} removes a table with all its rows:

\begin{sqlblock}
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT
);
ALTER TABLE users ADD COLUMN active INTEGER NOT NULL DEFAULT 1;
DROP TABLE users;
\end{sqlblock}
